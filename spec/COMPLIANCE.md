## Interpretation applied

The model is ONE conforming implementation of a pre-Release-6 MIPS32 processor, Release 2 feature set,
big-endian, with an FPU. A feature may be absent ONLY IF the manual marks it optional (or "required if X is
implemented") AND the model's configuration registers truthfully declare it absent. Everything the manual marks
Required for that implementation must exist and behave as written. UNPREDICTABLE / UNDEFINED / implementation-
dependent behaviour may be pinned to any outcome the manual permits; the limits (MD00086 Vol II-A Rev 6.06,
section 1.2, p.3-4) are in E.2.

**Exact profile.** `Config.AT = 0` (MIPS32), `Config.AR = 1` (Release 2; the encoding also covers Release 3 and 5, with
"all features introduced in Release 3 and Release 5 ... optional", Vol III Table 9.64 p.234), `Config.BE = 1`,
one hart, no MIPS16e / microMIPS (`Config1.CA = 0`), no DSP / MT / MSA / VZ / SmartMIPS / MCU modules, no EJTAG
(`Config1.EP = 0`), no coprocessor 2 (`Config1.C2 = 0`), no caches (`Config1.IL = DL = 0`), no watch registers
(`Config1.WR = 0`), no performance counters (`Config1.PC = 0`), a Fixed Mapping MMU (`Config.MT = 3`, see B11),
FPU present (`Config1.FP = 1`: the FPU itself is optional, Vol II 3.1.1 p.29-30, the owner chose to have one) with
`FIR.F64 = 0` (32-bit FPU, `Status.FR` reads 0), `FIR.S = D = W = L = 1`, `FIR.PS = 0`, `FIR.Has2008 = 0`
(legacy NaN encoding, arithmetic ABS/NEG).

## Where the working interpretation is refined or contradicted by the manual

1. **"Absent only if declared"** cannot be applied literally to everything: the manual defines no declaring bit
   for Soft Reset, NMI, Supervisor Mode (beyond the field reading zero), `LLAddr` (pre-Release 5) or `ErrCtl`;
   there the manual's own mechanism is "If this bit is not implemented, it must be ignored on write and read as
   zero" (e.g. Status.SR, p.193). Those rows are marked `optional-absent(declared by: no ... bit exists)`. For
   features whose declaring bit lives in Config3 the declaration is that bit, read as 0; for Config4/Config5
   features it is `Config3.M = 0` (no Config4, hence no Config5). "Config3: Required if any optional feature
   described by this register is implemented: Release 2 of the Architecture, the SmartMIPS™ ASE, or trace logic"
   (Vol III 9.48 p.245) lists "Release 2 of the Architecture" among the features, so Config3 is required on this
   Release 2 profile; F17 (done) implements Config2 = `0x8000_0000` and Config3 = 0 as read-only registers with
   `Config1.M = 1`. Config4's Compliance line repeats the words "Release 2 of the Architecture" (9.49 p.253), but
   every Config4 field describes a TLB/scratch-register extension the profile does not have, Config3.M reads 0 "If
   the Config4 register is not implemented" (p.245), and the Release 2 manual says Config3.M "should always read as
   a 0" (MD00090 Vol III Rev 2.50 §8.29 p.110): Config4 stays absent (A9.49).
2. **"Required must behave as written"** is unsatisfiable for the L format: the manual requires `FIR.L = 1` on a
   Release 2 FPU (Vol I Table 6.4 p.85) and in the same breath makes every L-format result UNPREDICTABLE with
   `FR = 0` (MD00086 CVT.L.fmt p.154). See D-note 2 for the minimal consistent reading.
3. **User Mode is REQUIRED**, not optional: "The MIPS32 and microMIPS32 PRA requires two operating modes: User
   Mode and Kernel Mode." (Vol III ch.3 p.21). Only Supervisor and Debug Mode are optional. Since wave 3 (F9) the
   model has both: `kernelMode s` = UM = 0 or EXL or ERL (Vol III 3.2 p.21, `KSU = UM || 0` without Supervisor Mode),
   `userMode s` = not Kernel Mode (3.4 p.22), `cp0Usable s` = Kernel Mode or CU0 (3.5.3 p.23). Since wave 4 (F10) the
   User-Mode address checks are modeled too (B9).
4. **`Config.MT = 0` ("None") is not a described organization.** The only non-TLB MMUs with a defined
   translation are Fixed Mapping (`MT = 3`) and BAT (`MT = 2`) (Vol III Appendix A, p.313-319; Vol I 2.4.2 p.32).
   "no MMU / fixed mapping" are two different things in the manual. See B11/B12. Since wave 4 (F10) the model declares
   and implements `MT = 3`.
5. **A halt is not a permitted pin for UNPREDICTABLE behaviour** ("must not halt or hang the processor",
   MD00086 p.4), and is tolerable for UNDEFINED behaviour only if "The assertion of any of the reset signals
   must restore the processor to an operational state" (p.4); the model has a Reset exception since wave 3
   (`resetException`, F8), which the environment applies (there is no reset input to `step`). The manual is also
   inconsistent on whether ERET/WAIT in a delay slot are UNPREDICTABLE (BEQ p.72) or UNDEFINED (ERET p.177, WAIT p.442).
6. **Supervisor Mode may not be combined with the minimal MMU**: "Supervisor Mode is not supported with a Fixed
   Mapping MMU." (Vol III A.1.1 p.313).

## Verdict legend and counts

`conforms`; `permitted pin` (an UNPREDICTABLE / UNDEFINED / implementation-dependent case resolved to an outcome the
manual permits); `DEPARTURE` (the model does something the manual's DEFINED text does not allow);
`MISSING-REQUIRED` (a feature the profile requires is absent or only partly there);
`optional-absent(declared by <bit>)`; `optional-absent(NOT declared: ...)` (optional, absent, but no readable bit says so);
`n/a (outside profile)` (Release 6 only, MIPS64 only, later release: the encoding must raise RI/CpU, which it does);
`n/a (environment, not architecture)` (a model/harness convention on which the manual states nothing, so there is no manual text to conform to or to pin: E16).
`conforms (case: permitted pin: ...)` marks a row whose behaviour conforms but which contains one UNPREDICTABLE / UNDEFINED / implementation-dependent case pinned to a permitted outcome (counted under permitted pin).
Rows are counted once per table row; A.2/A.3 repeat A.1's root causes at field level and are not counted. One root
cause often appears in several sections (for example "no address translation" shows up in A, B, C and E); the root causes
are listed once, in order, in section F. The counts above were recomputed from the table rows (A.1 only for A), last in Wave 12c; a row whose
Verdict cell names several categories is counted once, under the first of MISSING-REQUIRED, DEPARTURE, optional-absent, n/a,
permitted pin, conforms that it names.

Global pins that are not repeated on every instruction row: an odd FP register number for a double with
`FR = 0` (UNPREDICTABLE, Vol III 3.5.2 p.22) uses the pair (N, N+1); a QNaN result for two QNaN operands copies the
first operand (Vol I 6.3.1.5 p.82 does not say which).

## A. CP0 registers (Vol III chapter 9)
Source of the "Compliance Level" quotes: `python3 docs/tools/compliance.py cp0` (67 sections 9.4 .. 9.70; sections 9.1-9.3
are the summary, notation and "Writing CPU Registers"). 9.15/9.16 share one Compliance line with 9.17 (p.157); 9.21's
page is image-only in the text extraction and was read from the PDF (p.169).

How absence is declared for the registers below:

* TLB registers (Index, Random, EntryLo0/1, Context, PageMask, Wired, EntryHi, PageGrain): "Required for TLB-based
  MMUs; Optional otherwise"; the declaration is `Config.MT <> 1` (Table 9.64, p.235).
* Config3 is "Required if any optional feature described by this register is implemented: Release 2 of the
  Architecture, the SmartMIPS™ ASE, or trace logic" (9.48 p.245); the profile is Release 2, so Config3 is present
  (F17, done) and reads 0: every feature it describes is declared absent by its own bit (Table 9.67 p.245-251).
  Config2 is "Required if a level 2 or level 3 cache is implemented, or if the Config3 register is required"
  (9.47 p.241): present, `0x8000_0000` (`M = 1`, no L2/L3 cache). `Config1.M = 1` ("If the Config2 register is
  implemented, this bit should read as a 1", Table 9.65 p.237), `Config2.M = 1` (Table 9.66 p.241), and
  `Config3.M = 0` ("If the Config4 register is not implemented, this bit should read as a 0", Table 9.67 p.245)
  declares Config4/Config5 and every feature they describe absent.
* Everything else has its own Config1 bit: caches IL/DL, watch WR, performance counters PC, EJTAG EP, COP2 C2, MIPS16e CA.

### C.2 What the interrupt/timer subsystem must look like (design constraints taken from the manual)

* Interrupt request = (Cause.IP bit AND Status.IM bit) for IP7..IP0 in compatibility mode (Table 6.2, Vol III p.73), taken only
  when Status.IE = 1, EXL = ERL = 0 (p.72). Entry through the general vector offset 0x180 (Cause.IV = 0) or 0x200 (IV = 1), ExcCode
  Int (0) (6.2.26 p.102; Table 6.10 p.86: BEV=0/IV=1 -> 0x8000_0200, BEV=1/IV=1 -> 0xBFC0_0400).
* Table 6.1 (p.72-73) lists "x x =0 x x" (IntCtlVS = 0) as Compatibility; its "Not Allowed" row (p.73) is "BEV=0, IV=1, IntCtlVS **≠0**,
  VInt=0, VEIC=0". Compatibility mode "is in effect if ... IntCtlVS = 0" and dispatches through 0x200 when CauseIV = 1 (6.1.1.1, p.73;
  Table 6.10 p.86): conforming text, no contradiction and no pin (the text extraction loses the "≠" glyph; checked on the PDF page).
* Timer: Count/Compare, "When the value of the Count register equals the value of the Compare register, an interrupt request is
  made"; Cause.TI pending; cleared by a write to Compare; merged into the IP bit named by IntCtl.IPTI. Pin: `IPTI = 7` (HW5/IP7, the
  Release-1 placement, Vol III 9.30 p.187). `Cause.DC = 1` stops Count (9.36 p.210).
* Hardware interrupt lines HW0-HW5 (IP2..IP7) are external inputs: the model needs one input field (for example
  `State.hwIrq : BitVec 6`) that the environment drives; `mfc0 Cause` returns IP7..IP2 = hwIrq OR (TI at IPTI) and IP1..IP0 as written.
* An interrupt is taken between instructions: EPC is the address of the next instruction to execute, or the branch address with
  BD = 1 if that instruction is in a delay slot (Vol III 9.38 p.217: "For asynchronous (imprecise) exceptions, EPC contains the address
  of the instruction at which to resume execution"; Table 6.11 p.87).

### D-notes

1. **Global pins** (odd double register, two-NaN operand order, `FS` operand flushing) are described in the header, not repeated.
   "conforms" on a memory or branch instruction does not re-count the root causes in B (no User-Mode address checks, no
   translation) or E3 (delay-slot CTIs); `mfc0`, `mtc0`, `di`, `ei`, `eret`, `wait` raise Coprocessor Unusable outside Kernel/Debug
   Mode when CU0 = 0 (Vol III 6.2.22 p.100) since wave 3 (F9); `mfc0`/`mtc0` are `conforms` / permitted pin
   (D-rows, A9.n): the registers they once lacked (Count, Compare, HWREna in wave 5; IntCtl, SRSCtl, SRSMap in wave 6) exist, and the model has no
   MISSING-REQUIRED row.
2. **L format, FIR.L and the manual's inconsistency.** Quotes, in order:
   * Vol II 3.1.1, p.30 (and Vol I 2.4.1 p.30-31, same text): the allowable FPU subsets are "No FPU"; "FPU with S, and W formats and all
     supporting instructions. This 32-bit subset is permitted by Release 6, but prohibited by pre-Release 6 releases."; "FPU with S, D, W,
     and L formats and all supporting instructions ... pre-MIPSr5 permits this 64-bit configuration, and allows both FPU register modes.
     Status.FR=0 support is required but Status.FR=1 support is optional."; and the PS variant. (Both volumes print the FIR bits with typos:
     "FIR.S=FIR.L=1, FIR.D=FIR.L=FIR.PS=0", "FIR.S=FIR.L=FIR.D=FIR.L=1".)
   * Vol I Table 6.4, p.85, Release 2 row, 32-bit FPU (FIR.F64 = 0): "64-bit data formats D/L use even/odd pairs: FIRD=1 and FIRL=1 required";
     footnote 3: "Release 2, Release 3, and Release 5 required S, D, W and L data formats."; MD00086 revision history 5.03, p.469: "Volume I, Section
     2.2 'Compliance ad Subsetting' noted that the L format is required in MIPS FPUs, to be consistent with Table 5.4 'FIR Register Field Definitions'."
   * Against that, MD00086 CVT.L.fmt p.154 (the same sentence on CEIL.L, FLOOR.L, ROUND.L, TRUNC.L, CVT.S.L/CVT.D.L pages): "The result of this
     instruction is UNPREDICTABLE if the processor is executing in the FR=0 32-bit FPU register model; it is predictable if executing on a 64-bit
     FPU in the FR=1 mode, but not with FR=0, and not on a 32-bit FPU." and Vol III 3.5.2, p.22: "UNPREDICTABLE under ... The FR bit is 0,
     64-bit operations are enabled, and a floating-point instruction is executed whose datatype is L or PS", where 3.5.1 says 64-bit operations are
     "enabled if the F64 bit in the FIR register is 1" - so Vol III does not make L UNPREDICTABLE on a 32-bit FPU (F64 = 0) while Vol II does.
   * **Minimal consistent reading**: `FIR.F64 = 0`, `FIR.S = D = W = L = 1`, `FIR.PS = 0` (the one pre-Release-6 subset with D and a 32-bit register
     model that Table 6.4 allows), and every L-format instruction (and LUXC1/SUXC1) pinned, per its own page ("UNPREDICTABLE ... with FR=0"), to
     any permitted outcome: the cheapest is the Reserved Instruction exception the model already raises ("UNPREDICTABLE operations may cause
     arbitrary exceptions", Vol II 1.2.1 p.3). It is the only reading that satisfies the subset list (p.30), Table 6.4, the revision-history note
     and the instruction pages at once; `FIR.L = 0` matches no allowed pre-Release-6 subset. Upgrades (optional, F18): execute the L format on
     even/odd pairs (also permitted), or implement `FR = 1` (`FIR.F64 = 1`, Status.FR R/W), which makes L, LUXC1, SUXC1 predictable.
3. **Multi-format entries.** ABS/ADD/C.cond/DIV/MADD/MOV/MOVF/MOVN/MOVT/MOVZ/MSUB/MUL/NEG/NMADD/NMSUB/SQRT/SUB .fmt: S and D implemented, `.PS`
   absent (`FIR.PS = 0`, RI). CVT.D.fmt / CVT.S.fmt: the W and S/D sources implemented, the L source is the L format (D-note 2).
4. **Assembly idioms** (B, BAL, EHB, NOP, SSNOP, NAL): the manual lists them as idioms; `Asm.lean` accepts `b`, `bal`, `nop`, `ssnop`, `ehb`
   (`Asm.lean`); `pause` and `nal` have assembler mnemonics too (since `6b88488`) and decode as the instructions the manual says they alias
   (`sll $0,$0,5`, `bltzal $0`; SPEC-NOTES 9.16), so no idiom lacks a mnemonic.
5. **EVA group** (16 entries): "Implementation of this instruction is specified by the Config5EVA field being set to one" (e.g. LBE p.212);
   EVA is "an optional Enhanced Virtual Addressing (EVA) feature" of Release 3 (Vol III 4.1.5 p.26).
6. **JR.HB / JALR.HB**: the hazard barrier clears "all execution and instruction hazards" (Vol II p.208); the model has none, so `ClearHazards()` is
   vacuous. Since 7R the hint field is checked: hint 0 is `jr`/`jalr`, hint `10000` is `jrHb`/`jalrHb` (own constructors), any other hint is
   Reserved Instruction (JR p.207: "the only defined hint field value is 0"; D95, D96, D100, D101).

### E.2 What UNPREDICTABLE and UNDEFINED permit (MD00086 Vol II-A Rev 6.06, 1.2, p.3-4)

Permitted for UNPREDICTABLE: results "may vary from processor implementation to implementation, instruction to instruction, or as a function
of time"; the operation "may cause a result to be generated or not. If a result is generated, it is UNPREDICTABLE"; it "may cause arbitrary
exceptions". Not permitted: depending on "any data source (memory or internal state) which is inaccessible in the current processor mode";
to "read, write, or modify the contents of memory or internal state which is inaccessible in the current processor mode" ("For example,
UNPREDICTABLE operations executed in user mode must not access memory or internal state that is only accessible in Kernel Mode or Debug Mode
or in another process"); and, verbatim: "UNPREDICTABLE operations must not halt or hang the processor".
Permitted for UNDEFINED (1.2.2 p.4): "operations or behavior may vary from nothing to creating an environment in which execution can no longer
continue" and "may cause data loss"; the one restriction: "must not cause the processor to hang (that is, enter a state from which there is no
exit other than powering down the processor). The assertion of any of the reset signals must restore the processor to an operational state".

Consequences for the model: (a) `branchInDelaySlot`, `noInstruction`, `unhandledException` were halts of the modeled machine, outside
what an UNPREDICTABLE operation may do; since `f620266` `step` never halts (F3, F6, F7 done) and the last two are only the hosted run's stopping conventions (`Env.lean`); (b) for the UNDEFINED ERET/WAIT-in-delay-slot cases a halt would be tolerable only with a reset that restores
operation (the model has one since F8), but BEQ p.72 puts the same instructions under UNPREDICTABLE, so the safe pin is an exception (F3; the
model raises RI, in every mode, before the CP0 usability check); (c) "unaligned/odd register"
style pins that only choose a result or raise RI are fine; (d) a pin must not make the outcome depend on user-inaccessible state: now that User Mode
exists (F9), an UNPREDICTABLE user-mode operation may not, for example, read Kernel memory or CP0 state to compute its result.
